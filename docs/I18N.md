# UI languages (English + Hebrew, more later)

Status: **phases A and B are built** (language setting, all UI text translated, AI output in the chosen language). **Phase C (full RTL layout) is designed but not built.**

---

## 1. Goals and non-goals

**Goals**
- The UI language can be English or Hebrew. English is the fallback.
- **Smart default:** on first launch the device language is pre-selected if the app supports it, otherwise English.
- The user picks the language on first launch and can change it any time in Settings.
- All UI text follows the chosen language (phase B).
- **AI output that the app writes for the user follows the chosen language:** "More info" place summaries and the refinement `note`.
- Adding a language later = one dictionary file + one line in the app registry + one line in the server registry. No other code changes.

**Non-goals (explicit)**
- **No translation of trip content.** Titles, activity names, notes, place queries stay in the source language exactly as today (`DESIGN.md` 1.2 and 3.2 rule 2). `create-trip` does not receive the language. A Hebrew UI showing an English plan (and the reverse) is expected and correct.
- No full RTL layout flip in A/B (that is phase C). In a Hebrew UI the layout stays left-to-right; only the strings change.
- No dark mode, no per-trip language, no server-side storage of the user's language.

## 2. Design

### 2.1 App: files

```
mobile/src/i18n/
  languages.ts   # the registry: the only list of supported languages
  en.ts          # source dictionary; its shape is the type every other language must match
  he.ts          # Hebrew dictionary, typed as Dict
  detect.ts      # pickLanguage(deviceCodes): pure, testable, no Expo imports
  index.ts       # useT(), getT(), useLang(), re-exports
```

### 2.2 Registry (`languages.ts`)

```ts
import { en } from './en';
import { he } from './he';

export const LANGUAGES = {
  en: { nativeName: 'English', dir: 'ltr', locale: 'en-US', dict: en },
  he: { nativeName: 'עברית', dir: 'rtl', locale: 'he-IL', dict: he },
} as const;

export type Lang = keyof typeof LANGUAGES;
export const DEFAULT_LANG: Lang = 'en';
export const LANG_CODES = Object.keys(LANGUAGES) as Lang[];
export function isLang(x: unknown): x is Lang { return typeof x === 'string' && x in LANGUAGES; }
```

`dir` is stored now but only used in phase C. `locale` feeds `Intl` date formatting.

### 2.3 Dictionaries (`en.ts`, `he.ts`)

- `en.ts`: `export const en = { ... }` (no `as const`, so values widen to `string`), then `export type Dict = typeof en`.
- `he.ts`: `export const he: Dict = { ... }`. **A missing or extra key is a type error**, so `npx tsc` catches incomplete translations. No runtime cost, no library.
- Group keys by screen/feature: `common`, `tabs`, `myTrips`, `plan`, `create`, `join`, `share`, `refine`, `activity`, `participants`, `original`, `settings`, `language`, `namePrompt`, `samples`, `sync`, `errors`, `crash`, `a11y`.
- Strings with values or plurals are **functions**, so each language handles its own grammar (Hebrew has a dual form):
  ```ts
  // en
  days: (n: number) => (n === 1 ? '1 day' : `${n} days`),
  tooLongPlan: (max: string) => `The plan is too long (max ${max} characters).`,
  // he
  days: (n: number) => (n === 1 ? 'יום אחד' : n === 2 ? 'יומיים' : `${n} ימים`),
  ```
- Rotating loading messages (`use-rotating-message.ts` callers) become arrays in the dictionary: `create.loading: ['…', '…']`.
- Hebrew style: short, natural, gender-neutral where practical (prefer infinitive/imperative plural forms or nouns, e.g. "שמירה" over "שמור/שמרי").

### 2.4 Access (`index.ts`)

```ts
export function useLang(): Lang { return useStore((s) => s.lang); }
export function useT(): Dict { return LANGUAGES[useLang()].dict; }
/** For non-React code (api.ts errors, share message). Reads the current store value. */
export function getT(): Dict { return LANGUAGES[useStore.getState().lang].dict; }
export function getLocale(): string { return LANGUAGES[useStore.getState().lang].locale; }
```

Usage: `const t = useT();` then `t.settings.title`, `t.common.days(n)`. Because `useT` subscribes to the store, changing the language re-renders every screen immediately (no restart in A/B).

### 2.5 Store (`store.ts`)

- New persisted fields: `lang: Lang` and `langChosen: boolean` (true once the user confirmed a language, on first launch or in Settings).
- New action: `setLang(lang)` sets both.
- **Bump `version` to 2** and extend `migrate`: v1 → v2 adds `lang: pickLanguage(deviceCodes())`, `langChosen: false`. Existing installs then see the first-launch picker once, pre-selected with the smart default. Add `lang`, `langChosen` to `PersistedState` and `partialize`.
- Initial state (fresh install): `lang: pickLanguage(deviceCodes())`, `langChosen: false`. So even before the picker, the app already renders in the detected language.

### 2.6 Smart default (`detect.ts`)

```ts
/** First supported language from the device's preferred list, else English. */
export function pickLanguage(deviceCodes: (string | null | undefined)[]): Lang
```
- Normalize: lowercase, take the part before `-`/`_`. Map the legacy Android code **`iw` → `he`** (older Android versions report Hebrew as `iw`).
- Walk the list in order, return the first code that `isLang`. Otherwise `DEFAULT_LANG`.
- `deviceCodes()` (in `index.ts`, not in `detect.ts`) = `getLocales().map((l) => l.languageCode)` from **`expo-localization`** (install with `npx expo install expo-localization`; it is included in Expo Go). Wrap in try/catch → `[]`.

### 2.7 First-launch picker

- New `components/language-prompt.tsx`, built on the existing `Dialog` (like `name-prompt.tsx`): heading, one row per `LANGUAGES` entry showing `nativeName` (always in its own script, so a user can find their language whatever the current UI language is), the current one selected, and a Continue button.
- Selecting a row switches `lang` immediately (live preview: the dialog text changes language); Continue calls `markLangChosen` / `setLang`. Android back = keep the selected (detected) language and mark chosen. No tap-outside close.
- Shown once on My Trips (`app/(tabs)/index.tsx`) when the store is hydrated and `langChosen === false`. It must not collide with `NamePrompt` (that one appears only at first create, later).
- The list is rendered from `LANG_CODES`, so a new language appears automatically.

### 2.8 Settings

- New "Language" section in `app/(tabs)/settings.tsx` above "About": the same option rows (a small shared `LanguageOptions` component used by both the prompt and Settings). Tapping applies immediately and sets `langChosen`.
- Show a one-line hint under it: AI descriptions are written in the chosen language; trip plans stay in their original language.

### 2.9 Server: language registry

New `supabase/functions/_shared/languages.ts`:
```ts
export const AI_LANGUAGES = { en: "English", he: "Hebrew" } as const;
export type Lang = keyof typeof AI_LANGUAGES;
/** Unknown or missing → "en". Never put client text into a prompt; only these names. */
export function resolveLang(x: unknown): Lang
```
Old app builds send no `lang` → English, so the server change is backward compatible.

### 2.10 Server: place summaries ("More info")

- `place-info` reads `lang = resolveLang(body.lang)`.
- `describePlace(query, lang)`: the system prompt becomes a function of the language name: "Write 2-3 sentences in {Hebrew} …". Add: "Write proper names the way they are commonly written in {language}; if there is no common form, keep the original name." The "I don't have reliable information" sentence is also in that language.
- **Cache key becomes `(place_key, lang)`.** Today the key is only the place, so the first viewer's language would be served to everyone. With the language in the key, two participants of the same trip each get their own language, and each (place, language) pair is generated once.
- New migration `supabase/migrations/20261013000000_place_info_lang.sql`:
  ```sql
  alter table public.place_info add column lang text not null default 'en';
  alter table public.place_info drop constraint place_info_pkey;
  alter table public.place_info add primary key (place_key, lang);
  ```
  Existing rows are English, so `default 'en'` labels them correctly. Check the actual constraint name before running (`\d place_info`).
- Function: `.eq("place_key", key).eq("lang", lang)` and `upsert({ place_key, lang, summary, model })`.

### 2.11 Server: refinement note

- `refine-trip` reads `lang`; `refinePlan(plan, source, instruction, lang)`.
- Prompt rules 6 and 8: replace "(one short sentence, in English)" with "in {language}". **Rule 4 is unchanged** (content keeps its language; new content follows the instruction's language). This is the only change; the plan itself is never translated.
- Today the server falls back to the English string `"No changes were made."` when the AI returns `changed: false` with no note. Instead return `{ trip, note, changed: false }` and let the app show `t.refine.noChanges` when `note` is null. Add `changed` to the response type in `api.ts` (optional, so old/new mismatches don't break).

### 2.12 Errors

- Server keeps English messages (logs, curl, old app builds). **The app translates by `code`.**
- `errorMessage(err)` in `api.ts`: `getT().errors[err.code]` if present, else the server message, else `getT().errors.generic`.
- `errors` dictionary keys (from the current server and app): `bad_pdf`, `pdf_no_text`, `too_large`, `too_long`, `empty`, `not_a_plan`, `refused`, `ai_failed`, `not_owner`, `not_found`, `nothing_to_undo`, `nothing_to_redo`, `code`, `db`, `bad_codes`, `bad_query`, `bad_request`, `config`, `timeout`, `network`, `no_token`, `generic`.
- Codes used by more than one endpoint with different meanings (`empty`, `too_long`, `ai_failed`) get a context-neutral translation, or the caller passes a context (`errorMessage(err, 'refine')`) and the dictionary has `errors.refine.too_long` overrides. Pick the simpler one that reads well.
- The `too_long` messages include a number: keep the number out of the translation (generic "The text is too long") or have the server add `max` to the error payload. Prefer the generic wording.

### 2.13 Dates

- `lib/dates.ts`: `shortDate`, `tripSummary`, `updatedLabel` take a `locale` (and `tripSummary` a `days(n)` function) instead of the hard-coded `'en-US'` / `'day'/'days'`. Callers pass `LANGUAGES[lang].locale` and `t.common.days`. Keep the functions pure so the Node tests still run without React.
- Hermes on Android supports `toLocaleDateString('he-IL', { month: 'short', day: 'numeric' })` → "14 באוק׳". Verify on the phone; if it falls back to English, use a small month-name array per language in the dictionary instead.
- `todayISO` is unchanged.

### 2.14 Share message and Join

- The share message (`share-modal.tsx`) becomes `t.share.message(title, code)`, for example `Join my trip '…' on TripPlan. Code: K7QX3M` / `הצטרפו לטיול '…' ב-TripPlan. קוד: K7QX3M`.
- `extractShareCode` (`lib/codes.ts`) today looks for the English word `code`. Make it language-agnostic: build the label pattern from **every** language's `share.codeLabel` (`code`, `קוד`, …), so a Hebrew message can be joined from an English UI and vice versa. Pass the labels in as a parameter (keeps `codes.ts` pure for tests). Add test cases for the Hebrew message, including a Latin title word that looks like a code (e.g. "GREECE").

## 3. Implementation (done)

Built in two phases, both done and checked on an Android phone on 2026-10-13.

**Phase A: language setting + AI in the chosen language.** `expo-localization` for the device language; the `src/i18n/` registry and detection; `lang` / `langChosen` in the store (version 2 with a migration); the first-launch picker and the Settings section; the server registry; `place-info` with `lang` and the `(place_key, lang)` cache key (migration `20261013000000_place_info_lang.sql`); `refine-trip` with `lang` and `changed`. Deploy order was migration → functions → app; every step is backward compatible (a missing `lang` means English).

**Phase B: all UI text through the dictionaries.** Every string the user can see or hear (titles, buttons, placeholders, empty states, dialogs, menus, loading messages, accessibility labels, errors, the share message, dates) comes from `en.ts` / `he.ts`. Sample titles are translated by sample id; sample texts are content and stay as they are. Full-width text blocks align by the UI language; rows and icons are not mirrored (that is phase C).

Tests: `pickLanguage` cases (`he-IL`, legacy `iw`, fallback order, empty) and Hebrew `shortDate` / share-message parsing in `mobile/tests/lib.test.ts`; `resolveLang` in `supabase/functions/_tests/languages.test.ts`; the smoke test checks that the same place returns Hebrew text for `he` and Latin text for `en` (the cache is split).

**Done when** (met): switching the language in Settings changes every visible string on every screen at once, with no restart, in both directions; More info and the refine note follow the language; trip content never changes.

## 5. Phase C (not built): full RTL layout for RTL languages

**Status: postponed.** It touches every screen's layout and can only be verified on a device, so it was left out of the MVP.

**What it is:** in Hebrew (any language with `dir: 'rtl'`), the whole layout mirrors: rows run right-to-left, back arrows and chevrons point the other way, the timeline line and day dots sit on the right, the tab bar order flips, text aligns right.

**How it works in React Native**
- RTL layout is global and native: `I18nManager.allowRTL(true)` + `I18nManager.forceRTL(isRtl)`. It applies **only after the JS bundle reloads**, so changing between an LTR and an RTL language must reload the app: `Updates.reloadAsync()` from `expo-updates` (works in Expo Go) after the store has saved the new language. Show a short "The app will restart to apply the language" confirmation.
- On startup, before the first render, compare `I18nManager.isRTL` with `LANGUAGES[lang].dir`; if they differ, call `forceRTL` and reload once (covers a first launch with a Hebrew device, and the persisted choice).
- Flexbox `row`, `marginStart/End`, `paddingStart/End`, `start/end` mirror automatically. Hard-coded `left`/`right`, `marginLeft/Right`, absolute positions and transforms do not, and must be changed to `start`/`end`.

**Known work and risks**
- **`contentTextStyle` (`lib/rtl.ts`):** with RTL layout on, RN swaps `textAlign: 'left'` and `'right'`. Content direction would invert (English notes aligned right, Hebrew left). Fix: compute alignment relative to the layout direction (`isRtl(text) !== I18nManager.isRTL ? 'right'/'left' swapped`), or use `writingDirection` plus `textAlign: 'auto'` and verify on Android. This is the most likely bug.
- Directional icons (Ionicons `chevron-forward`, `arrow-back`, etc.): flip with `transform: [{ scaleX: -1 }]` when RTL, or pick the mirrored icon. Non-directional icons stay.
- `timeline.tsx` (vertical line + dots), `overlays.tsx` (bottom sheet animations), swipe gestures, the tab bar, the header row in Trip Plan, text inputs (cursor side, placeholder alignment).
- Mixed content: an English trip in a Hebrew UI still needs per-string direction, which is exactly what `contentTextStyle` does today; keep it after the fix above.
- `expo-updates` must be installed (`npx expo install expo-updates`); confirm `reloadAsync` in Expo Go on the test phone first.
- Reload loses in-memory UI state (open sheets, unsaved inputs). Only Settings and the first-launch picker trigger it, so this is acceptable.

**Plan when it is time**
1. Install `expo-updates`, add the startup direction check + reload; language change between directions asks and reloads.
2. Replace `left/right` styles with `start/end` across `src/` (grep `Left|Right|left:|right:`).
3. Fix `contentTextStyle` for RTL layout + tests.
4. Mirror directional icons via a tiny `DirIcon` helper.
5. Walk every screen in Hebrew and English on the phone (both samples), then commit.

**Done when:** in Hebrew the app looks like a native RTL app on every screen; English is unchanged; Hebrew and English trip content both align correctly in both UI languages.

## 6. Adding a language later (checklist)

1. `mobile/src/i18n/xx.ts`: `export const xx: Dict = { ... }` (the compiler lists every missing key).
2. `LANGUAGES` in `languages.ts`: `xx: { nativeName, dir, locale, dict: xx }`.
3. `AI_LANGUAGES` in `supabase/functions/_shared/languages.ts`: `xx: "<English name>"`; deploy `place-info` and `refine-trip`.
4. If `detect.ts` has a legacy code for it (like `iw`), add the mapping.
5. RTL language before phase C: works, layout stays LTR. After phase C: mirrored automatically.

Nothing else changes: the picker, Settings, detection, cache key, share-code parsing and prompts all read the registries.
